# Battleships AI

H446 Computer Science A Level NEA Project

This repository contains the source code and writeup for my Computer Science A Level NEA project.  
The project scored **62 out of 70**.

## What it is

A web-based Battleships game with an AI opponent. The AI has multiple difficulty levels, ranging from random targeting to a smarter strategy that hunts down ships once it lands a hit.

## Contents

- `index.js` – Express web server entry point
- `logic/` – Core game logic
- `routes/` – API routes
- `public/` – Front-end files (`index.html`, `script.js`, `style.css`)
- `Programming Project Writeup.pdf` – Full project writeup

## My advice

**1. Use Git.**  
This was a lifesaver for me. Start out with a Git repository and make commits as you go when you make changes. 
This may seem unnecessary at first, but if you need to go back to show evidence of tests then you can checkout an old commit.

**2. Justification is everything.**  
For the development section, justify everything you do. Missing even a few pieces of evaluation can lose marks. 

**3. Show evidence.**  
In the development and evaluation sections, show the tests and the output of the tests - but also show screenshots of the output. Without this, you can lose marks. The evidence is required, even if the evidence proves nothing.  
A handy trick for doing this retrospectively is using Git. I was missing evidence for various failed tests. Instead of breaking the code again, I checked out a previous commit and ran the tests again.  

**4. Follow the structure of this writeup.**   
Do what you want, but I followed the structure of other writeups and then added my own structural changes. Read through it and at least pay mind to the structure.

**5. Get stakeholder feedback.**  
Even if the stakeholder is yourself. They don't need to know.

**6. Use numbered boxes in code screenshots.**  
I was struggling to annotate code screenshots. I eventually ended up with the idea of the white boxes with numbers. This is an easy way to then write about individual sections of the code in the screenshot. 

**7. Do progress reviews.**  
This was an idea I came up with which helps to score marks. Summarise the current progress of the solution.

**8. Refer to success critera.**  
Throughout development and evaluation, keep referring back to individual success criteria points. This is very important for marks.

**9. Put detail into a *"How well does the solution meet the success criteria?"* section of the Evaluation.**  
Refer to individual success criteria points with an explanation for each. Then explain how each of those were met or not met.

**10. Make individual testing videos and a full testing video.**  
Throughout the development, make videos showing the tests and outcomes. This is required for showing evidence. You can do this retrospectively by checking out old commits with Git.
Make one final testing video showing the entire solution. Mention this near the end of the writeup after Evaulation.
